# Apple Design — fluid UI skill

Источник: [emilkowalski/skills — apple-design/SKILL.md](https://github.com/emilkowalski/skills/blob/main/skills/apple-design/SKILL.md). Проверенная версия файла на 2026-07-21: SHA-256 `11840b24a11d7f94f39c6aaab074750ae4e4de4ef54ee4b1dd97e16ebd485e61`.

## Что это

Практический `SKILL.md` для AI coding agent: переводит подход Apple к интерфейсам и физичному motion на web. Фокус — жестовые UI (drag/swipe/sheet), spring-анимации, материалы/глубина, типографика и reduced motion.

**Факты из источника:** ключевой принцип — интерфейс должен отвечать сразу, отслеживать жест 1:1, наследовать скорость пользователя и допускать перехват/разворот анимации в любой момент. Автор связывает рекомендации с WWDC-докладами Apple; для реализации на web предлагает Pointer Events, `requestAnimationFrame` и spring-библиотеки вроде Motion/Framer Motion.

## Зачем Данилу

Это не генератор «Apple-стиля», а чек-лист качества взаимодействия для AI-собранных лендингов, CRM-экранов и прототипов. Особенно полезен там, где есть bottom sheet, drawer, карточки с drag/swipe, фильтры, мобильные панели и заметная microinteraction: типовой агент часто делает их визуально нормальными, но механически мёртвыми.

## Как применить

1. До реализации описать жест и состояние: откуда элемент появляется, куда возвращается, какие snap-points допустимы, что происходит при отмене.
2. Для touch/drag использовать Pointer Events с `setPointerCapture`; во время drag обновлять позицию непрерывно и учитывать точку захвата.
3. Для интерактивного движения выбрать spring, а не фиксированный CSS transition: начинать с текущего визуального значения, передавать velocity при отпускании, разрешать перехват анимации.
4. По умолчанию использовать спокойный critically damped motion; bounce добавлять только там, где его оправдывает импульс жеста.
5. До handoff проверить: мгновенный feedback на pointer-down, симметричный enter/exit путь, читаемость translucent-слоёв и режим `prefers-reduced-motion`.
6. Проверить интерактивный прототип руками до продакшн-кода, а не только статичный макет.

Мини-чек перед приёмкой:

- нет ли блокировки ввода во время перехода;
- не прыгает ли элемент при перехвате/смене направления;
- сохраняется ли контекст источника у popover/sheet;
- не заменяет ли blur/анимация иерархию и понятный UX;
- остаётся ли смысловой feedback при reduced motion.

## Ограничения и риски

- Это guidance, а не дизайн-система и не готовый компонент: параметры spring, жесты и доступность нужно валидировать в конкретном продукте.
- «Физичность» не равна постоянной анимации: лишний bounce, blur и haptics отвлекают и ухудшают доступность.
- CSS transitions и keyframes для gesture-driven элементов могут давать заметные скачки при перехвате; не применять рекомендацию без проверки поддержки выбранной motion-библиотекой.
- Веб не идентичен iOS: паттерны должны соответствовать платформе, устройству и задаче, а не имитировать Apple ради эстетики.
- `backdrop-filter` и сложные эффекты могут бить по производительности и контрасту; нужны fallback и проверка на слабых устройствах.

## Вывод Данила

Держать как точечный skill для экранов с управляемым пользователем движением. Не тащить его в каждый интерфейс: в статичном CRM-экране сначала важнее ясная иерархия, скорость и сценарий, а fluid motion — только для элементов, где он делает действие понятнее.
