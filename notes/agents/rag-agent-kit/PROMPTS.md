# PROMPTS — протокол сборки с Claude Code

> Восемь шагов. После каждого есть что проверить руками. Не склеивай их в один промпт: агент, собранный одной командой, выглядит рабочим и молча ошибается в трёх местах из восьми — а искать эти три ты будешь дольше, чем собирал.

Промпты ниже — рабочие формулировки, а не заклинания. Правь под свой проект: чем точнее ты опишешь свою предметную область, тем меньше придётся переделывать.

---

## Шаг 0. Подготовка

Скопируй `CLAUDE_TEMPLATE.md` в корень проекта под именем `CLAUDE.md` и допиши свои детали: что за продукт, кто пользователи, какой стек, что за корпус документов.

Это не формальность. `CLAUDE.md` читается в каждом сеансе и не даёт агенту дрейфовать в сторону своих привычек по ходу сборки.

**Проверка:** в корне лежит `CLAUDE.md`, в нём есть раздел про AI-агента и запрет на `temperature`/prefill.

---

## Шаг 1. Определить предметную область

```
Прочитай docs/rag-agent-kit/MANUAL.md и SPEC.md целиком.

Мой проект: [что это, для кого].
Корпус знаний: [что за документы, сколько их, откуда берутся].
Пользователи: [кто они, есть ли уровни доступа].
Схема аутентификации в проекте: [как я определяю текущего пользователя].

Задай мне вопросы, которые нужно закрыть до кода, — одним списком, не по одному.
Пока ничего не пиши.
```

Отвечай развёрнуто. Половина последующих переделок происходит из-за того, что на этом шаге на вопрос про уровни доступа ответили «пока не надо».

**Проверка:** вопросы заданы и касаются твоей предметной области, а не общих мест.

## Шаг 2. Схема данных

```
Примени миграцию docs/rag-agent-kit/migrations/001_agent_memory.sql.

Адаптируй под мой проект:
- заменить TODO на внешний ключ к моей таблице пользователей
- [если уровней доступа нет] оставить access_level везде 0, логику не выпиливать
- [если корпус уже есть в другой таблице] не дублировать: показать, как
  переиспользовать существующую таблицу вместо knowledge_documents

Миграцию 002 НЕ применяй — это Этап 2.
После применения перегенерируй типы БД.
```

**Проверка:** четыре таблицы созданы, RLS включена на всех, типы перегенерированы. Убедись глазами, что политики `deny_anon` на месте — не полагайся на отчёт.

## Шаг 3. Наполнить корпус

```
Напиши скрипт, который заливает мои документы в knowledge_documents из [источник].

Требования:
- upsert по slug, не insert: повторный запуск не должен плодить дубли
- после заливки вывести: сколько загружено, сколько пропущено, сколько с ошибками
- показать 3 случайные строки целиком, чтобы я проверил, что поля легли верно
```

**Проверка:** количество строк в базе совпадает с количеством файлов на входе. Открой три строки — в `body_md` полный текст, а не обрезок; `title` не пустой.

Это скучный шаг, который решает всё. Агент с кривым корпусом не чинится промптом.

## Шаг 4. Сборка контекста

```
Реализуй buildContext по разделу 4 SPEC.md.

Отдельным файлом, чистая функция, покрытая типами. Никакого any.
Особое внимание:
- флаг u в регулярке токенизации — иначе кириллица вырезается
- фильтр доступа ДО отсечения top-N
- пиннинг прямых ссылок по сырому тексту (токенизатор ест короткие токены)
- каталог строится всегда, даже когда контекст пустой

Затем напиши маленький скрипт, который вызывает buildContext с моим
вопросом и печатает: какие документы выбраны, их score и первые 200
символов каждого фрагмента.
```

**Проверка — самая важная во всей сборке.** Прогони скрипт на 5–7 реальных вопросах, которые тебе задают живые люди. Смотри не на код, а на выдачу: те ли документы нашлись? Если поиск промахивается — крути веса полей и стоп-слова **сейчас**, до того как сверху ляжет модель. Потом ты будешь думать, что виноват промпт, и править не то.

## Шаг 5. Основной эндпоинт

```
Реализуй POST и GET /api/agent-chat по разделам 2, 3, 5, 6 SPEC.md.

Соблюдай порядок восьми фаз буквально. Критично:
- сохранять сообщение пользователя ДО вызова модели
- system как массив блоков с cache_control, не строкой
- в system только то, что не зависит от вопроса (правила + каталог)
- НЕ передавать temperature/top_p/top_k — это 400 на текущих моделях
- НЕ использовать prefill — тоже 400
- max_tokens 2048: у Sonnet 5 мышление включено по умолчанию и ест тот же бюджет
- в GET по conversationId — проверка user_id, иначе читаются чужие треды
- generateTitle через void, с проверкой на уже проставленное название

Системный промпт возьми за основу из раздела 8 MANUAL.md и перепиши
под мою роль: [опиши роль агента].

После реализации прогони npx tsc --noEmit.
```

**Проверка:** `tsc` чист. Задай агенту вопрос через curl — приходит ответ с непустым `sources`.

## Шаг 6. Клиент

```
Собери страницу чата по разделу 8 SPEC.md: список сообщений, поле ввода,
оптимистичный рендер, карточки источников под ответом ассистента,
индикатор ожидания, отдельная обработка 503.

Стиль — как в остальном проекте, компоненты переиспользовать, не выдумывать
новую дизайн-систему.
```

**Проверка:** отправь вопрос из браузера. Ответ рендерится как markdown, источники кликабельны и ведут на реальные страницы, повторная отправка во время ожидания заблокирована.

## Шаг 7. Проверить экономику

```
Добавь временное логирование в эндпоинт: после вызова модели пиши в консоль
input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens.
```

**Проверка — фактом, а не верой.** Задай два вопроса подряд в одном треде. На втором `cache_read_input_tokens` **должен быть больше нуля**. Ноль означает, что кэш промпта не работает — ищи причину в разделе 6 MANUAL.md (чаще всего это дата в системном промпте или каталог, уехавший в сообщение пользователя).

Потом задай тот же первый вопрос в новом треде: должен вернуться `cached: true` и нулевой расход.

Убери логирование, когда убедился.

## Шаг 8. Приёмка

```
Пройди по критериям приёмки из раздела 9 SPEC.md.

Для каждого пункта: либо покажи, что он выполняется, с конкретным
подтверждением, либо честно скажи, что не выполняется, и почему.
Не отмечай выполненным то, что не проверял.
```

Затем — сам, руками, по `CHECKLIST.md`. Пункты про безопасность (чужой тред, утечка через кэш, уровни доступа) проверяй лично: это ровно те места, где отчёт «сделано» и реальность расходятся чаще всего.

## Если что-то пошло не так

| Симптом | Где искать |
|---|---|
| Отвечает не по документам, а «вообще» | Шаг 4: поиск не находит. Проверь выдачу `buildContext` напрямую |
| «Такого документа у меня нет», хотя он есть | Каталог не строится или не попал в `system` |
| Follow-up «а подробнее?» теряет тему | В пиннинг не передаются предыдущие реплики пользователя |
| Дорого | `cache_read_input_tokens` = 0. Раздел 6 MANUAL.md |
| Ответы обрываются на полуслове | `max_tokens` слишком мал — у Sonnet 5 мышление ест тот же бюджет |
| 400 от API | Остались `temperature` или prefill в запросе |
| Кириллица ломает поиск | В регулярке токенизации потерян флаг `u` |
| Пользователь видит закрытый контент | Фильтр доступа применяется после top-N, или уровень доступа не входит в ключ кэша |
