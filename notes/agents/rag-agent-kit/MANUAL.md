# RAG-агент с памятью — архитектура

> Как устроен AI-наставник в платформе курса AI-Архитектор и как собрать такой же. Читать до того, как давать Claude Code первую команду.

---

## 0. Главная мысль

RAG-агент — это **не** «модель, которую обучили на моих данных». Это обычный запрос к модели, перед которым твой код успел найти релевантные куски твоих документов и вклеить их в промпт. Всё. Никакого дообучения, никаких весов.

Отсюда следует то, что определяет всю архитектуру: **качество агента на 80% определяется качеством поиска, а не промптом.** Если поиск подсунул не тот документ — не спасёт ни одна инструкция. Если поиск подсунул правильный — ответ будет хорошим даже на посредственном промпте.

Поэтому в этом мануале про поиск и про память написано больше, чем про промпт.

## 1. Общая схема

```
                    ┌────────────────────────┐
                    │  UI чата (клиент)      │
                    │  messages[] + textarea │
                    └───────────┬────────────┘
                                │ POST /api/agent-chat
                                │ { userToken, conversationId, message }
                    ┌───────────▼────────────┐
                    │  Один серверный        │
                    │  обработчик, 8 фаз     │
                    └───┬──────────┬─────────┘
                        │          │
         ┌──────────────┘          └───────────────┐
         │                                          │
┌────────▼─────────┐                    ┌───────────▼──────────┐
│ ПАМЯТЬ (Postgres)│                    │ ЗНАНИЯ (Postgres)    │
│                  │                    │                      │
│ L1 история треда │                    │ knowledge_documents  │
│ L2 реестр тредов │                    │  ├ Этап 1: keyword   │
│ L3 кэш ответов   │                    │  └ Этап 2: pgvector  │
└──────────────────┘                    └───────────┬──────────┘
                                                    │
                                        ┌───────────▼──────────┐
                                        │  Anthropic Messages  │
                                        │  system: статика     │
                                        │   + prompt cache     │
                                        │  messages: история   │
                                        │   + контекст+вопрос  │
                                        └──────────────────────┘
```

Обрати внимание на разделение: **память и знания — разные вещи и живут в разных таблицах.** Память — что говорил конкретный пользователь. Знания — что вообще знает система. Их постоянно путают и сваливают в одну таблицу, после чего невозможно ни почистить историю, ни переиндексировать корпус.

### Почему без стриминга

Один POST, один `await`, один ответ. Никаких SSE, EventSource, ReadableStream.

Так сделано осознанно. Ответ на 800 токенов приходит за 3–7 секунд, спиннер «думаю…» это переживает. А взамен: кэш ответов работает только на целой строке (со стримингом его пришлось бы собирать по кускам), код обработчика — линейный, отладка — обычный лог.

Стриминг обязателен, когда ответы длиннее ~2000 токенов, когда нужна кнопка «отмена», или когда это голос. Если этого нет — стриминг стоит примерно втрое больше кода ради тридцати процентов ощущения скорости.

## 2. Четыре слоя памяти

Это ядро. Слово «память» в описаниях агентов обычно значит одно из четырёх разных явлений — и путаница здесь стоит дорого.

### L1 — короткая память: история треда

Последние N сообщений текущего разговора, которые уезжают в `messages[]` вместе с новым вопросом.

```ts
const { data: history } = await db
  .from('agent_messages')
  .select('role, content')
  .eq('conversation_id', conversationId)
  .order('created_at', { ascending: true })
  .limit(20);          // 10 пар «вопрос-ответ»
```

Почему 20, а не «всё». Каждое сообщение — это входные токены на каждом следующем запросе. Тред из ста реплик стоит на сотом сообщении в разы дороже, чем на первом, и качество от этого не растёт: модель тонет в собственных старых ответах. 20 — это примерно граница, после которой пользы уже нет.

**Что почти все делают неправильно:** сохраняют сообщение пользователя *после* успешного ответа модели. Модель падает по таймауту — вопрос исчез, пользователь смотрит на пустой экран и не понимает, отправилось ли. Сохраняй **до** вызова модели.

### L2 — длинная память: реестр тредов

Таблица разговоров: `id`, `user_id`, `title`, `last_message_at`, `archived_at`. Даёт список «мои прошлые чаты», к любому можно вернуться.

Название треда генерируется **отдельным дешёвым вызовом в фоне** после первого ответа — Haiku, 30 токенов, `void` без `await`:

```ts
void generateTitle(db, apiKey, conversationId, firstMessage);   // не ждём
```

Стоит доли копейки, название появляется у пользователя через полторы секунды после ответа и ничего не блокирует. Внутри — проверка «а не проставлено ли уже название» перед вызовом, иначе при попадании в кэш ответов генерация запустится второй раз.

### L3 — кэш ответов: память о вопросах

Если два человека спросили одно и то же — второй получает готовый ответ, не потратив ни одного токена.

Ключ — SHA-256 от **нормализованного** вопроса. Нормализация: нижний регистр → выбросить пунктуацию → разбить на слова → выбросить стоп-слова и слова короче трёх букв → **отсортировать** → склеить.

```ts
export function normalizeQuery(q: string): string {
  return q.toLowerCase().trim()
    .replace(/[^\p{L}\p{N}\s]/gu, ' ')
    .split(/\s+/)
    .filter((w) => w.length >= 3 && !STOP_WORDS.has(w))
    .sort()                          // ← из-за этого порядок слов не важен
    .join(' ');
}
```

Сортировка — это то, что делает кэш полезным: «как подключить Supabase» и «Supabase как подключить» дают один хеш.

Три правила, каждое из которых куплено болью:

1. **В ключ обязательно входит уровень доступа пользователя.** `${hashQuery(msg)}:${accessLevel}`. Иначе бесплатный пользователь получит из кэша ответ, сгенерированный для платного — по контексту, к которому у него нет доступа. Это утечка платного контента через кэш, и она абсолютно бесшумная.
2. **Кэшируется только первое сообщение треда.** Всё, что дальше, зависит от истории, а историю нормализовать невозможно. `const cacheable = priorMessages.length === 0;`
3. **TTL.** У нас 30 дней. Материалы меняются — вечный кэш начинает отвечать про то, чего уже нет.

### L4 — база знаний: память о мире

Собственно корпус: `knowledge_documents`. Не память пользователя, а память системы. Живёт отдельно, переиндексируется независимо, чистится независимо.

### Плюс пятый слой — кэш промпта на стороне Anthropic

Не память, а деньги. Статическая часть промпта помечается `cache_control`, и Anthropic при повторных запросах читает её примерно в 10 раз дешевле. Подробно — в разделе 6.

## 3. Восемь фаз одного запроса

Порядок не случайный: дешёвые проверки идут раньше дорогих, а короткие замыкания — раньше вызова модели.

### Фаза 1 — авторизация и валидация

```ts
if (!process.env.ANTHROPIC_API_KEY) return json({ error: 'unavailable' }, 503);
if (!body?.message || body.message.length > 2000) return json({ error: 'invalid' }, 400);

const user = await resolveUser(body.userToken);        // ← своя схема аутентификации
if (!user) return json({ error: 'unauthorized' }, 401);
```

Лимит длины сообщения — не формальность. Без него любой желающий вклеивает в поле ввода мегабайт текста и платит за это твоей карточкой.

Отдельный 503 при отсутствующем ключе — чтобы в проде видеть «админ не выставил переменную», а не «что-то пошло не так».

### Фаза 2 — получить или создать тред

Нет `conversationId` — создаём новый и возвращаем клиенту вместе с ответом, чтобы следующее сообщение пришло уже в него.

### Фаза 3 — жёсткие гейты (до вызова модели)

Если есть темы, которые этот пользователь не должен получить ни при каких обстоятельствах — проверка идёт **до** модели, и модель просто не вызывается: возвращается фиксированный текст.

```ts
const blocked = detectRestrictedTopic(body.message, user.accessLevel);
if (blocked) {
  await persistBoth(conversationId, body.message, GATE_RESPONSE[blocked]);
  return json({ conversationId, response: GATE_RESPONSE[blocked], gated: blocked });
}
```

**Почему не хватает инструкции в промпте.** Модель знает про твою предметную область не только из твоего контекста, но и из обучения. Инструкция «не рассказывай про X» снижает вероятность утечки, но не обнуляет её. Если утечка стоит дорого — не вызывай модель вообще.

**И сразу про грабли.** Мы сначала сделали широкие списки ключевых слов: «оплат», «демо», «продаж». Результат — обычные рабочие вопросы блокировались пачками, потому что это нормальные слова человеческой речи. Сузили до узкоспецифичных фраз, которые не встречаются случайно. Правило: жёсткий гейт защищает **одну-две по-настоящему дорогие вещи**, а не «всё, что не для этого тарифа». Остальное отсекается фильтром доступа в поиске (фаза 6) — тихо и без ложных срабатываний.

### Фаза 4 — история + сохранение вопроса

Читаем L1, сохраняем сообщение пользователя. Именно в таком порядке — иначе только что сохранённый вопрос попадёт в историю сам к себе.

### Фаза 5 — кэш ответов

Только если `priorMessages.length === 0`. При попадании: сохранить ответ как обычное сообщение ассистента, инкрементировать `hit_count`, вернуть с флагом `cached: true`. Модель не вызывается.

### Фаза 6 — сборка контекста (ядро RAG)

Раздел 4 целиком про это. На выходе:

```ts
const { context, catalog, sources } = await buildContext(message, user.accessLevel, 8, priorUserText);

const userMessageWithContext = context
  ? `${context}\n\n---\n\nВопрос: ${body.message}`
  : `Вопрос: ${body.message}\n\n(Поиск не нашёл совпадений в базе. Ответь из общих знаний,
     но если вопрос про конкретный документ — скажи, что не нашёл его.)`;
```

Ветка «ничего не нашлось» важнее, чем кажется. Без неё модель на пустом контексте начинает уверенно сочинять содержание твоих документов.

### Фаза 7 — вызов модели

```ts
const response = await anthropic.messages.create({
  model: 'claude-sonnet-5',
  max_tokens: 2048,
  system: [{ type: 'text', text: systemPromptText, cache_control: { type: 'ephemeral' } }],
  messages: [...priorMessages, { role: 'user', content: userMessageWithContext }],
});
```

Что здесь важно и разобрано отдельно ниже: что лежит в `system` и что в `messages` (раздел 6), почему именно такой `max_tokens` (раздел 7).

### Фаза 8 — запись и фон

Сохранить ответ вместе с источниками, обновить `last_message_at`, положить в кэш ответов (если первый ход), запустить генерацию названия фоном, вернуть ответ.

Источники **нормализовать перед записью**: в базу и на клиент едут `{ kind, slug, title }`, без внутренних `score` и `snippet`. Служебные веса релевантности в API-ответе — это и лишний вес, и подсказка тому, кто захочет реверсить твой поиск.

## 4. Этап 1: поиск по ключевым словам

Это то, что реально работает у нас в проде. Никаких эмбеддингов.

### Алгоритм

**1. Токенизация вопроса.** Нижний регистр, выбросить всё кроме букв и цифр (`\p{L}\p{N}` — важно, иначе кириллица умрёт), отсеять стоп-слова и слова короче трёх символов.

**2. Скоринг каждого документа.** Считаем вхождения токенов, поля взвешиваем — попадание в заголовок стоит втрое дороже попадания в тело:

```ts
const score = scoreText(doc.title, tokens) * 3
            + scoreText(doc.summary, tokens)
            + scoreText(doc.body_md, tokens) * 2;
```

Веса подбираются под свой корпус: у нас основной носитель знания — конспект, поэтому у него вес 2, а не 1.

**3. Фильтр доступа — ДО отсечения top-N.**

```ts
if (!canAccess(user.accessLevel, doc.access_level)) continue;   // ← до сортировки
```

Это не косметика. Отфильтруй после — и недоступные документы вытеснят доступные из восьмёрки, а пользователь получит ответ «по общим знаниям» при том, что нужный ему документ в базе есть.

**4. Пиннинг по прямой ссылке.** Если человек пишет «расскажи про урок 14» — никакой скоринг не гарантирует, что урок 14 попадёт в top-N: длинные документы по частотности его перебьют. Поэтому прямые ссылки распознаются регуляркой **по сырому тексту** (токенизатор выбрасывает «14» как слишком короткое) и получают заведомо максимальный вес мимо отсечения:

```ts
const LESSON_REF_PATTERNS = [
  /урок[аеуоми]*\s*№?\s*(\d{1,2})/gi,
  /(\d{1,2})\s*-?\s*(?:й|го|м|ой)?\s*урок/gi,
];
```

Плюс матч по полному названию документа — под кнопку «спросить про этот документ», которая подставляет заголовок в поле ввода.

И ещё: в пиннинг подаётся не только текущий вопрос, но и **последние 2–3 реплики пользователя**. Без этого follow-up «а подробнее?» теряет, о чём вообще шла речь.

**5. Вырезка фрагмента.** Не весь документ, а окно ~1400 символов вокруг первого вхождения искомого слова, с многоточиями по краям. Восемь документов целиком — это десятки тысяч токенов на каждый запрос; восемь фрагментов — три-четыре тысячи.

**6. Сборка блока.**

```
# Релевантные материалы

[Документ 1] Как подключить Supabase MCP (slug: supabase-mcp)
…фрагмент…

---

[Документ 2] …
```

Slug в заголовке — чтобы модель могла на него сослаться, а UI — превратить ссылку в рабочую карточку.

### Каталог: приём, который убирает «такого документа нет»

Отдельно от найденных фрагментов в **системный** блок вклеивается компактный список **всех** доступных пользователю документов — номер, название, отметка «закрыто» для недоступных.

Зачем. Без каталога модель видит только восемь найденных фрагментов, и на вопрос «а что в документе 12?» честно отвечает «у меня нет такого документа» — хотя он есть, просто не попал в top-N. Пользователь делает вывод, что система дырявая.

Почему каталог живёт в `system`, а не в тексте вопроса: он **не зависит от вопроса** и меняется только при смене уровня доступа. Значит, внутри одного разговора он побайтово одинаков — и не ломает кэш промпта. Положишь его в сообщение пользователя — кэш будет промахиваться на каждом ходу, потому что рядом лежит меняющийся вопрос.

### Когда переходить на векторы

Не «когда захочется по-взрослому», а по симптомам:

- корпус перевалил за ~500 документов, и скоринг всего корпуса в памяти стал заметен по времени;
- вопросы формулируются смыслом, а не терминами («как не потерять клиента после первой встречи» — ни одного слова из документа);
- пользователи спрашивают синонимами и переформулировками, и ты видишь по логам, что поиск промахивается.

Пока ни один симптом не проявился — векторы дадут тебе более сложную систему с той же точностью.

## 5. Этап 2: векторный поиск

Когда критерии сработали.

**Чанкинг.** Документ режется на куски 500–1500 символов с перекрытием 10–15%. Резать по смысловым границам (заголовки, абзацы), а не по счётчику символов посреди слова. Перекрытие нужно, чтобы мысль, оказавшаяся на стыке, не потерялась.

**Эмбеддинги.** У Anthropic нет своего эндпоинта эмбеддингов — это нормально и это не проблема. Мы используем **Voyage AI, модель `voyage-3`, 1024 измерения**: на русском она заметно точнее массовых альтернатив. Важная деталь, которую пропускают: при индексации `input_type: 'document'`, при поиске `input_type: 'query'` — это разные режимы, и путаница в них тихо роняет качество.

**Хранение и индекс.** `vector(1024)` в Postgres, индекс `ivfflat` с `vector_cosine_ops`. Индекс строить **после** заливки данных: построенный по пустой таблице, он будет плохо кластеризован.

**Поиск.** SQL-функция принимает эмбеддинг запроса и возвращает top-N по косинусной близости выше порога. Готовая — в `migrations/002_knowledge_vectors.sql`.

**Гибрид — то, ради чего стоит остаться на связи с Этапом 1.** Чистый вектор плохо ловит точные совпадения: артикулы, аббревиатуры, «урок 14», названия функций. Рабочая схема — оба поиска параллельно, объединение и переранжирование. Пиннинг по прямой ссылке из раздела 4 при переходе на векторы **никуда не девается**: он решает ровно ту задачу, которую семантика не решает в принципе.

> **Что дальше.** Переранжирование гибридной выдачи, оценка качества поиска на размеченном наборе вопросов, дообучение порогов под свой корпус — это уже отдельная работа, и делается она по метрикам, а не по ощущению «вроде получше». Здесь дан рабочий каркас, а не пайплайн оценки.

## 6. Кэш промпта: где экономятся 90%

Правило одно, и из него следует всё: **кэш — это совпадение префикса.** Anthropic считает хеш от промпта до метки кэша. Изменился один байт в начале — недействительно всё, что после.

Порядок сборки: `tools` → `system` → `messages`. Значит:

| Куда | Что кладём | Кэшируется |
|---|---|---|
| `system` | Роль, правила ответа, каталог, надстройки под уровень доступа | да |
| `messages` | История треда, найденный контекст, сам вопрос | нет |

```ts
system: [{ type: 'text', text: systemPromptText, cache_control: { type: 'ephemeral' } }]
```

Экономика: запись в кэш стоит 1.25× от обычного входа (5-минутный TTL), чтение — около 0.1×. Окупается со **второго** запроса. TTL продлевается при каждом попадании, так что у активного пользователя кэш живой весь сеанс.

### Три способа тихо убить кэш

1. **Дата или время в системном промпте.** `Сегодня ${new Date()}` в начале — и кэш не сработает никогда. Ни ошибки, ни предупреждения: просто `cache_creation_input_tokens: 0` навсегда. Нужна дата — клади в конец сообщения пользователя.
2. **Промпт короче минимума.** Минимальный кэшируемый префикс зависит от модели: 512 токенов для Opus 5, 1024 для Sonnet 5, 4096 для Haiku 4.5. Короче — молча не кэшируется. Наш системный промпт вместе с каталогом это перекрывает, а вот голый промпт на 3 КБ у Haiku не закэшируется вообще.
3. **Меняющийся набор инструментов или смена модели посреди разговора.** `tools` идут перед `system` — правка там обнуляет всё. Кэш привязан к модели.

**Проверять фактом, а не верой:** в ответе есть `usage.cache_read_input_tokens`. Если он ноль на повторных запросах — кэш не работает, ищи невидимого убийцу из списка.

## 7. Выбор модели и настройки, август 2026

Актуальные идентификаторы: `claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5`.

| Роль | Модель | Почему |
|---|---|---|
| Основные ответы | `claude-sonnet-5` | Лучший баланс цены и качества под ответы по контексту |
| Сложные разборы, архитектура | `claude-opus-5` | Когда цена ошибки выше цены токенов |
| Названия тредов, классификация | `claude-haiku-4-5` | Копейки за вызов, качества хватает |

### Три ловушки, на которых спотыкается перенос старого кода

**1. У Sonnet 5 мышление включено по умолчанию.** Если параметр `thinking` не передан — модель всё равно думает, и `max_tokens` ограничивает **мышление плюс ответ вместе**. Код, где стоял `max_tokens: 1024` под модель предыдущего поколения, начнёт обрезать ответы на середине. Либо подними `max_tokens` (2048 — разумный старт), либо выключи явно: `thinking: { type: 'disabled' }`.

**2. `temperature`, `top_p`, `top_k` больше не принимаются** — на текущих моделях это ошибка 400, а не игнорирование. Управляй поведением промптом. Если `temperature: 0` стояло ради воспроизводимости — она и раньше не гарантировалась.

**3. Prefill убран.** Предзаполнение последней реплики ассистента (`{ role: 'assistant', content: '{"' }` ради форсирования JSON) отдаёт 400. Нужен строгий JSON — используй структурированный вывод, а не хак с prefill.

Модель называется «Tool Use», не «function calling» — последнее из терминологии OpenAI и в коде Anthropic смотрится как признак того, что автор не читал документацию.

## 8. Системный промпт

Скелет, который держит поведение. Дальше подставляешь свою роль.

```
Ты — [роль]. Помогаешь [кому] разобраться в [чём].

# Как отвечать

1. Опирайся на переданный контекст — это фрагменты реальных материалов. Цитируй,
   объясняй своими словами, делай выводы.
2. Дополняй знаниями по технологиям, но связывай с материалами. Не читай лекций.
3. Не выдумывай содержание материалов. Полный список — в блоке «Каталог» ниже.
   Если документ ЕСТЬ в каталоге, но его текста нет в контексте — назови тему
   и предложи открыть; не утверждай, что документа не существует.
4. Ссылайся на источники: "📚 Подробнее: [slug]". Только на те, что в контексте.
5. Кратко и полезно: 3–7 предложений плюс список, если он нужен.
6. Русский язык. Технические термины — можно по-английски.
7. Эскалация: если вопрос за пределами материалов — [куда отправлять].
```

Пункт 3 — прямое следствие каталога из раздела 4, и без него каталог работает вполсилы.

Динамические надстройки (ограничения по уровню доступа, защита конкретных тем) **приклеиваются к системному блоку**, а не к сообщению пользователя — иначе теряется кэш. Они меняются редко и не зависят от вопроса, так что префикс остаётся стабильным внутри разговора.

## 9. Экономика

Наш профиль: ~150 пользователей, ~3 вопроса в день каждый, контекст 3–5 КБ.

| Показатель | Значение |
|---|---|
| Входные токены на запрос | ~5 000 (системный + каталог ~2K, контекст ~3K, история ~500) |
| Выходные токены | ~500 |
| Попадание в кэш промпта | ~70% после прогрева |
| Попадание в кэш ответов | ~25% на типовых вопросах |

Порядок величин на Sonnet 5: без кэша ~1.5 цента за запрос, с прогретым кэшем — в разы дешевле. На 13 500 запросах в месяц это десятки долларов, а не тысячи. **Актуальные цены проверяй в документации — они меняются, и у Sonnet 5 сейчас действует вводная цена.**

Куда уходят деньги, если уходят: раздутый контекст (не режешь фрагменты — платишь за целые документы), сломанный кэш (см. раздел 6), безлимитная длина сообщения, отсутствие кэша ответов при типовых вопросах.

## 10. Грабли

Каждая из них однажды случилась в проде.

**Кэш ответов без уровня доступа в ключе.** Платный контент утекает бесплатным пользователям через кэш. Молча. Ключ = хеш вопроса + уровень доступа.

**Загрузка чужого треда.** Читаешь тред по `conversationId` из запроса — обязательно проверяй `user_id = текущий пользователь`. Иначе перебором идентификаторов читается чужая переписка.

**Каталог в сообщении пользователя.** Кэш промпта промахивается на каждом ходу. В `system`.

**Широкий гейт по ключевым словам.** Обычные слова языка режут нормальные вопросы. Только узкоспецифичные фразы.

**Фильтр доступа после top-N.** Недоступные документы вытесняют доступные, пользователь получает «ничего не найдено» при полной базе.

**Сохранение вопроса после вызова модели.** Модель упала — вопрос исчез.

**Чужеродные документы в общем корпусе.** У нас запись отдельного платного продукта лежала в той же таблице, что и уроки курса, и по внутренней нумерации конфликтовала с первым уроком. Пользователи, не купившие продукт, получали цитаты из него. Исключай явно, по slug, на этапе выборки.

**Токенизатор съедает короткие токены.** «14» короче трёх символов и выбрасывается. Прямые ссылки на документ ищи регуляркой по сырому тексту.

**Генерация названия без проверки идемпотентности.** При попадании в кэш ответов фоновая генерация запускается второй раз. Проверяй `if (conv?.title) return;` первой строкой.

**Таймаут serverless-функции.** По умолчанию бывает 10 секунд — большой контекст в них не укладывается. Выставляй явно (`maxDuration = 60`) и убедись, что рантайм — Node, а не Edge, если используешь серверные библиотеки.

**Внутренние поля источников в ответе API.** `score` и `snippet` наружу не отдаются.

## 11. Что дальше

Собранное по этому мануалу — рабочий агент-отвечатель. Дальше начинаются вещи другого класса сложности, и каждая тянет за собой свою архитектуру:

- **Агент, который действует, а не отвечает** — Tool Use: агент вызывает твои функции, читает результат, продолжает. Меняется цикл обработки: вместо одного вызова — петля до `stop_reason === 'end_turn'`, с гейтами на необратимых действиях.
- **Мультиагентная схема** — оркестратор классифицирует запрос и роутит специализированным агентам со своими промптами, инструментами и бюджетами. Это уже не «чат по документам», а операционная система для команды агентов, с учётом стоимости каждого действия.
- **Наблюдаемость и стоимость** — дерево запусков, стоимость каждого шага, слои памяти с провенансом. Без этого агент, который стоил $100 в месяц, однажды стоит $3000, и ты не знаешь почему.
- **Контур под 152-ФЗ** — self-hosted Postgres в РФ, маскирование персональных данных до отправки в модель, RLS по ролям, аудит.

Каждое из этого разбирается в курсе AI-Архитектор — там же, где живёт агент, по образцу которого написан этот мануал.
